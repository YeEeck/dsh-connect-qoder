# Spec — 空闲窗口、排队耐心与流空闲天花板

**Status:** ready-for-agent
**Category:** bug + enhancement
**Effort:** stream-idle-patience
**Date:** 2026-10-22

词汇一律按 [`CONTEXT.md`](../../CONTEXT.md)：**单次请求**、**排队**、**每日限额**、**空闲窗口**、
**排队耐心**、**流空闲天花板**。裁定见 [ADR-0001](../../docs/adr/0001-patience-knob-exposure.md)。

## Problem Statement

用户在一次长回答进行到六十秒左右时被截断，答案在中间断掉，卡片上写着 `502 upstream_error`。
换一个时段，一条本来九十秒就会放行的排队请求直接失败，同样报 `502`——读起来像"Qoder 挂了"，
而真实原因是"排着队，等等就好"。这两件事都会在最糟糕的时刻发生：跑长程任务、开子代理、或者
一次提交了多步工具调用之后。

用户没有任何办法调整"我愿意为排队等多久"。这个数字被写死在插件里，而 0.7.4 之后它已经成了
唯一的重试来源：宿主不再对队列失败做兜底重试。

## Solution

**一、让计时器衡量沉默，而不是衡量总时长。** 单次请求只要还在持续产出，跑多久都不会被打断。
真正卡死的连接会在空闲窗口到期时被判定，并按阶段处理：还没开始输出就卡住，等于什么都没发出去，
可以安全重试；已经开始输出再卡住，重试会重复用户已经看到的内容。

**二、把"排队的失败"与"Qoder 坏了"分开。** 排队失败以一个可重试的状态返回，并在文案里说明
已经等了多久、重发会重新计时；不再统一压成 `502`。

**三、给用户一个旋钮：排队耐心，三档（2 / 4 / 6 分钟），默认 4 分钟。** 空闲窗口与流空闲天花板
由所选档位推导，用户不需要也不可能配出互相矛盾的组合。

## User Stories

1. 作为一个跑长程任务的用户，我希望生成到两三分钟的回答不会因为总时长而被切断，这样我不用把一次
   任务拆成好几段重跑。
2. 作为一个用子代理的用户，我希望子代理的一次单次请求不会在中途失败，因为那会连带打断整条
   工作流，而我很难把失败的那一步单独重放。
3. 作为一个遇到排队的用户，我希望九十秒就能放行的请求真的等下去，而不是在第六十秒被判死。
4. 作为一个遇到排队的用户，我希望看到"正在等待 Qoder 放行"，而不是"Qoder 出错了"，因为两者
   该做的事完全不同——一个是等，一个是换时间或去看账号。
5. 作为一个遇到排队的用户，我希望失败时被告知已经等了多久，这样我能判断是立刻重发还是先去做别的。
6. 作为一个遇到排队的用户，我希望失败文案说明重发会重新计时，这样我知道重发是有意义的，而不是
   又一次白等。
7. 作为一个上游卡住的用户，我希望在还没开始输出时判定失败并自动重试，因为那时重试不会产生重复内容。
8. 作为一个上游卡住的用户，我希望在已经开始输出后被判定失败时**不要**自动重试，因为重复的半截
   答案比一次干净的失败更糟。
9. 作为一个上游只发心跳不发内容的用户，我希望插件自己先判定卡死，而不是等到宿主那一层以更粗糙的
   方式超时并被盲目重试五次。
10. 作为一个上游卡住的用户，我希望被打断时能立刻释放连接，而不是拖着。

11. 作为一个用户，我想在卡片上用下拉框选择排队耐心，因为那里已经是我调其他设置的地方。
12. 作为一个用户，我想看到三档而不是一个自由数字，因为我不想去解几个超时值之间的关系。
13. 作为一个用户，我想默认值是"4 分钟"，因为这是大多数人能接受的等待上限，而它同时让现有的
    两分钟行为保持不变。
14. 作为一个用户，我想选择"6 分钟"时其他相关限度跟着自动调整，而不是由我手动同步。
15. 作为一个用户，我想选择"2 分钟"时也不会把某个内部值调到会自我否定的大小。
16. 作为一个用户，我想我的选择立刻对下一次单次请求生效，而不是要重启 DSH。
17. 作为一个用户，我想设置被保存并在重开卡片后仍然显示我选的那一档。
18. 作为一个改过配置文件的用户，如果我写了一个不存在的档位，我希望能看到明确的告警，而不是
    静默用回默认值。

19. 作为一个维护者，我希望"空闲窗口 < 排队耐心 < 流空闲天花板"这条不等式由构造保证，而不是靠
    两个常量碰巧满足大小关系。
20. 作为一个维护者，我希望失败按阶段分类这件事有测试钉住，因为把顺序改回去会让可重试的失败变成
    终态失败，而这在界面上看起来只是"换了个报错"。
21. 作为一个维护者，我希望空闲窗口按"产出可解析帧"重新计时，而不是按"收到字节"，因为我们和宿主
    量的必须是同一个东西——否则宿主会先触发，而我们那条带分类的错误永远用不上。
22. 作为一个维护者，我希望每一次单次请求的耐心从零起算，因为跨请求累计会让一次多步工具调用在
    后面莫名失败。
23. 作为一个维护者，我希望 `lib/` 产物与源码同一次提交，因为 CI 有新鲜度门禁。

## Implementation Decisions

**空闲窗口的语义**：从"整条流的绝对期限"改为"距离上一次产出可解析帧的间隔"。等待响应头也在这个
窗口内。每产出一个 chunk 重新计时；只发字节但不构成帧（心跳、残缺行）不算进度。

**按阶段的分类**：空闲窗口到期抛一个哨兵错误；重试循环在**第一帧之前**把它翻译成可重试的排队
拒绝（沿用现有的可重试错误类型，带 `retryAfterSeconds`），在**第一帧之后**翻译成不可重试的普通
错误。这个分界点是承重的，必须有独立测试钉住顺序。

**不能只靠 abort 一个 signal**：实测在较长窗口下，abort 事件会触发但挂起的读取不会跟着拒绝，
会把这次单次请求拖到运行时的传输层超时，并以误导性的错误收场。因此计时器必须与读取**显式竞速**，
abort 只用来释放 socket。读取的收尾清理（取消 body）同样要有边界，否则卡住的 socket 会让生成器
停在清理阶段，错误永远到不了重试循环。

**耐心的可注入性**：单次请求的入口增加一个可选的限制参数（空闲窗口、排队耐心），不传时使用模块
默认值。等待计算函数同样接受可选的预算参数。这样测试可以传小值，不需要真的等两分钟。

**档位与推导**：设置项是一个枚举，三档取值分别对应排队耐心 2 / 4 / 6 分钟，默认 4 分钟。
空闲窗口为排队耐心的一半（60 / 120 / 180 秒）；流空闲天花板为排队耐心加 60 秒（180 / 300 / 420 秒）。
选择"一半"是因为空闲窗口必须明显小于耐心，否则一次超时就会吃掉大半预算；选择"加 60 秒"是为了让
外层始终比内层宽松一档，同时保证内层总是先触发。

**为什么是枚举而不是数字**：枚举让"越界"从根上消失——没有可越界的值。用户手改配置写成不存在的
档位时，schema 解析失败；读设置的那一侧必须回落到默认档并留下可见告警，不允许静默用默认值。

**生效时机**：每次单次请求读一次当前档位，与宿主读流空闲天花板的节奏一致。档位变化需要重建
provider profile 才能让天花板跟进，走的是设置保存后已有的刷新链路，不需要重启。

**失败文案**：排队耐心花完时的错误必须包含"已等待约 X 秒"与"重发会重新计时"。空闲窗口到期时的
错误说明的是"上游多久没有输出内容"——两者是不同的失败，不共用一句文案。

**每日限额不受影响**：它仍然在排队之前判定、仍然不可重试。

## Testing Decisions

**什么算好测试**：只断言外部可观察的行为——产出、抛出的错误的类别与可重试性、尝试次数、错误文案
里对用户可见的部分。不断言内部计时器的实现、不断言私有函数名。每个测试都必须在明显短的墙钟时间
内结束（用注入的窗口值，不真的等）。

**主测试缝**：现有的 `streamChat` 入口，配一个被桩替换的全局 `fetch`，返回一个可以"停住不动"的
响应流。这是**已有**的缝，`chat-stream-reader.test.js` 与 `chat-protocol-drift.test.js` 都这么用。
不需要新缝，也不需要真的起一个回环服务器。

**次测试缝**：等待计算函数直接单元测试（`upstream-protocol.test.js` 的既有做法），以及流空闲
天花板的推导作为纯函数直接测试（新模块，无 peer 依赖，可被裸 `node --test` 直接 import）。

**配置契约**：沿用 `config-schema.test.js` 的做法——对源码文本断言字段已声明、带 volatile、
与保存白名单的字段名一致。注意该文件里的字段清单是硬编码的，新增字段必须同时把它加进去，
否则"每个字段都 volatile"这条承诺对新字段是空的。

**卡片**：`card-dom.test.js`（jsdom）断档位下拉存在、保存时带上所选值、重开卡片时回显。

**七个必须覆盖的场景**（前六个是本次缺陷的回归集，第七个是新增面）：

| 上游行为 | 期望 |
|---|---|
| 健康、快 | 产出 chunk，正常结束 |
| 健康、沉默短于空闲窗口但长于旧的绝对期限 | 正常结束（钉住缺陷 A） |
| 响应头后沉默，随后流恢复 | 重试后**成功** |
| 响应头后一直沉默 | 可重试的排队拒绝，尝试次数 > 1，受耐心约束 |
| 一个 chunk 后沉默 | 不可重试的错误，不重试，不重复产出 |
| 完全等不到响应头 | 可重试的排队拒绝（既有行为） |
| 只发心跳不发内容 | 在空闲窗口到期时判定失败（钉住"按帧计时"） |

**先红后绿**：这七个场景先写成红的，再改实现。

## Out of Scope

- 不改宿主的重试策略集合（`TIMEOUT` 仍留在可重试集合里；本 spec 靠不等式保证它不先触发）。
- 不给"每日限额"加任何旋钮。
- 不把 `QUEUE_WAIT_MAX_SLEEP_MS` 变成设置项，也不改为由其它值推导（已决定保持常量）。
- 不按 region 分别设置耐心（全局一个值）。
- 不新增数字输入控件。
- 不做流级别的保活/心跳注入：宿主那一层不解析 SSE 注释，注入不解决问题。
- 不改宿主对空闲超时的文案（我们碰不到那条错误）。
- 不处理"用户手改 provider 配置导致天花板与实际不符"的场景，只在注释里说明。

## Further Notes

**交付分两次提交**：缺陷修复（空闲语义、分类、按帧计时、文案）先落地，设置面（档位、推导、
卡片）随后。这样修复本身仍然是一份可上游的补丁，而产品判断留在它自己的提交里。

**与并行会话的边界**：`AGENTS.md` 与 `docs/agents/` 当前有另一会话未提交的改动，本工作不触碰。

**事故接续**：`docs/issues/24` 收窄了交给宿主的重试集合，代价是插件阶梯成为唯一重试来源；
本 spec 的第二部分正是把这个代价变成用户可调的产品面。

`lib/` 是受版本管理的产物，每个改动 `src/` 的工单都必须重建并同一次提交。
