# 排队耐心的对外面：只暴露一个档位，其余三个值推导

## 背景

`streamChat` 里原本有两个硬编码常量：`ATTEMPT_TIMEOUT_MS`（一次尝试多久没动静算卡死）与
`QUEUE_WAIT_BUDGET_MS`（单次请求愿意为排队花多久）。0.7.4 的 `ROUTE_RETRY_POLICY` 把宿主
的重试集合收窄到 `EMPTY_RESPONSE` / `TIMEOUT` / `TRANSPORT` 之后，插件自己的阶梯成了
唯一的重试来源，于是这个预算事实上就是用户能等多久的全部。

2026-10-22 的讨论结论：用户值得拥有这个旋钮，因为排队深度随区域与时段变化，240 s 对一个人够、
对另一个人不够。但代码里有四个数值，其中三个互相约束：

- 空闲窗口必须 ≥ `QUEUE_WAIT_MAX_SLEEP_MS`，否则"按提示睡满再重连"会被自己的看门狗判死；
- 空闲窗口必须 ≤ 排队耐心，否则它永远不触发，是个死旋钮；
- 排队耐心必须 < 流空闲天花板。**这一条是最贵的**：天花板是 Host 对插件这条流的看门狗，
  而 `TIMEOUT` 在 `ROUTE_RETRY_POLICY` 的可重试集合里，所以一旦天花板先触发，Host 会以
  全新的一套耐心重试最多 5 次——每次都是从零开始的排队，同时还多消耗 5 次 Qoder 每日额度。

## 决定

**只暴露一个旋钮：排队耐心的档位（<select> 三档）。空闲窗口按档位推导，流空闲天花板按档位
推导；`QUEUE_WAIT_MAX_SLEEP_MS` 保持常量。**

推导保证不等式由构造成立，用户无法配出违反它的组合。

## 被否的选项

**暴露两个旋钮，其余推导。** 用户要自己解 `30 s ≤ 空闲 ≤ 耐心` 这个不等式；而解错的方向里，
空闲 > 耐心 只是让旋钮失效，耐心 > 天花板会直接触发上面那条 5 次重试的放大链，卡片上不会有
任何提示。凡"必须满足 A < B 的两个值"，只暴露一个、另一个由它推导——这与 `MAX_SLEEP` 被否掉
的理由是同一形状。

**暴露数字输入而非档位。** 客户端没有任何持久化的数字输入先例（`type="number"` 在整个 client
里零命中），这意味着要新增解析、空值、NaN、越界四条失败路径，每条都要有用户可见状态（红线 1），
而分支覆盖率距地板只剩 0.27pp。下拉走的是现有先例（逐模型图像模式也是 select），分支数几乎不增。
档位也让"越界"从根上消失——档位不可越界。

**钳制越界值。** 用户设 900 s、实际生效 270 s 是静默失败，红线 1 明令禁止。改用 schema 的
`.min()/.max()` 让保存当场失败。

**无限等待。** 对子代理场景更糟：把"失败"变成"悬挂"，而且没有任何东西会让它结束。

## 后果

排队耐心花完时，失败消息必须写明已等待多久、以及重发会重新计时——否则用户只知道"失败了"，
不知道再发一次是有意义的。

流空闲天花板不再是 300 s 这个固定值，而是随档位推导；`retry.ts` 里"budget stays well under
the 300 s idle ceiling"这条注释从"运气好成立"变成"由构造保证"。
